# feedback-triage

## このスキルが解決すること

FB がチャット・コメント・問い合わせにバラバラに溜まり「何から手を付けるか」が決まらない。種別と優先度で仕分け、適切なスキル/プロセスに流す。

1. **分類**: バグ / 改善 / 要望 / 仕様確認 / 重複
2. **優先度**: 影響度 × 頻度（+ ピッチ直結か）
3. **振り分け**: 次に動かすスキル/プロセスを指定

## 起動方法

### slash command
`/feedback-triage [<FB>]` で起動。

### 自律起動
「このFBを分類して」「要望を整理」「優先度つけて」などで自動起動。

## 分類体系（[triage-rubric.md](./references/triage-rubric.md)）

`vercel-toolbar-loop` の 4 分類（視覚修正 / 文言修正 / 機能追加要望 / バグ報告）を土台に、ソース非依存に拡張:

| 種別 | 定義 | 振り分け先 |
|---|---|---|
| バグ | 仕様通り動かない | 修正 → `smoke-test`/`deploy-preflight` |
| 改善 | 動くがUX/品質を上げたい | `design-review` / `shadcn-ui` |
| 要望 | 新機能 | `spec-writer`（要件化） |
| 仕様確認 | 仕様が曖昧/認識相違 | `spec-writer`（仕様に戻す） |
| 重複 | 既出 | 既存項目に集約 |

## 優先度

`P1（致命/ピッチ阻害）> P2（重要）> P3（あれば）`。影響度 × 頻度で決め、ピッチ直前はデモ主導線の阻害を最優先。

## 出力

結果表には **バグ** / **改善** / **要望** / **仕様確認** / **優先度** を機械的に読める表記で含める。該当する FB がない分類は「改善: 該当なし」のように明記し、分類語が欠けないようにする。

## やってはいけないこと

- 全部「要望」にして優先度を付けない
- 仕様の認識相違を「バグ」として実装で握りつぶす（`spec-writer` に戻す）

## 周辺

- `vercel-toolbar-loop`: Toolbar 由来 FB の取得・分類の元
- `spec-writer`: 要望/仕様確認の行き先
- `experiment-plan`: 「効果が不明な改善」は実験で検証
