# experiment-plan

## このスキルが解決すること

「良かれと思った改善」が実は効いていない/悪化、を防ぐ。**仮説 → 指標 → 判定基準**を先に決めてから変更する。

1. **仮説**: 何を変えると何が良くなるか（理由つき）
2. **成功指標**: analytics-events のどのイベントで測るか
3. **判定基準**: どうなったら採用/棄却か、期間/対象

## 起動方法

### slash command
`/experiment [<仮説>]` で起動。

### 自律起動
「A/Bテストしたい」「この改善の効果を検証」「成功指標を決めたい」などで自動起動。

## 実験計画（docs/experiments/<name>.md）

[experiment-template.md](./references/experiment-template.md) の型:
- **仮説**: 「CTA を上部に出すと sign_up が増える（目に入る回数が増えるため）」
- **変更**: A=現行 / B=CTA 上部
- **指標**: 主要 = `sign_up` 率（analytics-events）/ ガードレール = 直帰率
- **判定**: B の sign_up 率が A を一定以上上回り、ガードレール悪化なし
- **対象/期間**: 対象ユーザー / 期間 or サンプル数

## プロト段階の割り切り

- 厳密な有意差検定が回るトラフィックは無いことが多い → 「明確な方向性」を見る
- 実装は feature flag / 単純な出し分けで足りる（重い実験基盤は不要）
- 計測が無いと判定不能 → `analytics-events` を先に

## やってはいけないこと

- 指標と判定基準を決めずに変更だけ入れる
- 複数変更を同時に入れて何が効いたか分からなくする
- ガードレール指標（悪化を見張る指標）を置かない

## 周辺

- `analytics-events`: 成功指標の計測基盤（先に必要）
- `feedback-triage`: 「効果不明な改善」をここで検証に回す
- `spec-writer`: 採用された変更を仕様へ反映
