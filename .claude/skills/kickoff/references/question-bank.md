# 要件確認の質問バンク

通常モードで投げる問い。**全部聞かない。** 依頼の粒度に応じて 3〜5 問だけ選び、依頼文で既に埋まっている項目は飛ばす。
`idea-framing` の 6 問のうち「最初の一歩に効く」ものを抜粋・実務化したもの。

## コア 5 問 (まずここから 3〜5 個)

1. **誰が使う?** — 想定ユーザー (架空でも具体名・役割)。社内 / クライアント / エンドユーザー
2. **何ができれば成功?** — このプロト/機能で「これが動けば OK」の 1 文。ピッチで言いたいこと
3. **スコープはどこまで?** — 今回作る範囲 / 今回やらないこと。MVP の線引き
4. **データ・連携は?** — 扱うデータ、外部 API・DB・認証の要否 (→ ⑥コア機能の要否判断)
5. **見た目の温度感は?** — 既存トンマナ / 参考イメージ / こだわり度 (ピッチ用に作り込むか、動けばいいか)

## 状況別の追加問い (必要時のみ)

- **AI 機能あり**: どのモデル感 (品質重視 / 速度重視)? 入出力は? (→ `ai-feature`)
- **DB・認証あり**: ログイン方式は? ロール/権限は? (→ `firebase-backend`)
- **複数画面**: 画面遷移の起点と主要導線は? (→ `app-flow-designer`)
- **締切/見せる相手**: いつ・誰に見せる? (作り込み度とリリース経路の判断)

## 進め方の規律 (Naoya 3 原則)

- **相手のペースを奪わない**: 1〜複数問投げたら待つ。性急に結論へ急がない
- **「私が」で背負う**: 「一般的には」を避け「私の見方では」で意見を述べる。ただし誘導しない
- **形式句を避ける**: 「ご検討ください」でなく、具体的な対象・行動・期限に分解して問う

## 即作りモードでは

質問は**スキップ**。依頼文から最小限の前提だけ自分で置き、「この前提で最短で作ります」と 1 行宣言して着手。
前提が大きく外れそうな 1 点だけは確認してよい。
