# ai-eval

## このスキルが解決すること

「プロンプトを直したら別のケースが壊れた」「AI の出力が良いのか悪いのか主観でしか言えない」を止める。AI 機能に**評価の物差し**を与え、回帰で守る。

1. **評価項目**: 何を良しとするか（正確性 / 形式 / 安全性 / トーン）
2. **テストケース**: 入力 → 期待出力（または合否基準）のデータセット
3. **回帰評価**: 固定ケースを Vitest で回し、プロンプト変更の劣化を検知
4. **プロンプト版管理**: 入出力例・改善履歴・評価結果（旧 prompt-manager）

## 起動方法

### slash command
`/ai-eval [cases|regression|prompt]` で起動。

### 自律起動
「この AI 機能を評価したい」「プロンプト変更の回帰」「期待出力を決める」「プロンプトの履歴管理」などで自動起動。

## 評価の作り方（docs/ai/evals/）

- **評価項目**: ケースごとに「正確性 / 形式（zod 準拠）/ 安全性（ai-safety-check 観点）/ トーン」を 0-2 で採点 or 合否
- **テストケース**: [eval-template.md](./references/eval-template.md) の表形式。代表 + 境界 + 失敗系を含める
- **回帰**: 構造化出力（`generateObject`）は Vitest で schema 準拠と必須フィールドを固定検証。自由文は「含むべきキーワード / 含んではいけない語」で緩く判定
- **プロンプト版管理**: [prompt-versioning.md](./references/prompt-versioning.md)

## やってはいけないこと

- 評価基準を決めずに「なんとなく良い/悪い」で判断する
- 実 LLM 呼び出しを CI の必須スモークに入れる（不安定・コスト）。回帰は構造/キーワード判定を基本にし、LLM-as-judge は任意の手動評価に
- プロンプトを履歴管理せず上書きし続ける（改善が検証不能になる）

## 周辺

- `ai-feature`: 評価対象の AI 実装（セキュリティガードと合わせて品質を担保）
- `ai-safety-check`: 安全性観点の評価項目を供給
- `smoke-test`: 回帰テストの実行基盤（Vitest）
