# db-migration

## このスキルが解決すること

Firestore はスキーマレスなので「型を変えてデプロイ」しても**既存ドキュメントは旧形式のまま残る**。読み取りで落ちる・新旧混在で集計が狂う、を段階移行で防ぐ。

1. **後方互換読み取り**: 新コードが旧形式も読める状態を先に作る
2. **デュアルライト**: 書き込みを新形式に（必要なら新旧両方に）切替
3. **バックフィル**: Admin SDK スクリプトで既存データを新形式へ一括変換
4. **旧形式削除**: 全データ移行を確認してから互換コードと旧フィールドを掃除

## 起動方法

### slash command
`/db-migration [plan|backfill|verify|cleanup]` で起動。

### 自律起動
「フィールド名を変えたい」「コレクション構造を変更」「既存データの移行どうする」「バックフィルスクリプト書いて」などで自動起動。

## 段階移行（[migration-playbook.md](./references/migration-playbook.md)）

ユーザーが出力先を明示した場合は、そのパスを優先する。例: `docs/design/db-migration.md` と指定されたら、既定の `docs/ops/migrations/NNN-<name>.md` ではなく指定パスに移行記録を作成する。本文には **互換読み取り** / **デュアルライト** / **バックフィル** / **掃除** / **ロールバック** の見出しを必ず含める。

| 段階 | やること | 戻し方（ロールバック） |
|---|---|---|
| 1. 互換読み取り | 旧形式 → 新形式に正規化する読み取り層 | コード revert のみ |
| 2. デュアルライト | 新規書き込みを新形式へ | コード revert（旧読み取りは生きている） |
| 3. バックフィル | Admin SDK で既存データ変換（dry-run → 本実行） | 旧フィールドを残しているので再変換可能 |
| 4. 掃除 | 互換コード・旧フィールド削除 | **ここから先は戻れない**。十分寝かせてから |

移行記録は `docs/ops/migrations/NNN-<name>.md`（連番）に、目的・対象・手順・確認結果・ロールバック条件を残す。

## やってはいけないこと

- バックフィルを先に走らせる（書き込みが旧形式のままだと混在が再発生）
- dry-run なしで本番データを一括更新
- 段階 4（旧形式削除）を移行直後にやる（ロールバック手段を自分で消す行為）
- Security Rules の更新を忘れる（新フィールド/新コレクションが弾かれる・素通りする）

## 周辺

- `data-modeler`: 変更後スキーマの設計と docs/design/data-model.md の更新（設計の正はあちら）
- `firebase-backend`: CRUD・Security Rules・Admin SDK の実装基盤
- `mockdata-ja`: 移行ロジックの検証用データ
- `observability-setup`: 移行中の読み取りエラー監視
